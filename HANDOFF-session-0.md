# Session 0 handoff

Built in one session from the mid-term draft deck. Everything here is a starting point to review, not a finished product.

## What exists
- `README.md`, `WORKPLAN.md`, `project.config.json` (example manifest)
- `agents/`: orchestrator, qc-critic, qc-debugger (markdown instruction files, ~1 page each)
- `skills/`: nine SKILL.md drafts with frontmatter descriptions tuned to trigger from a user's phrasing
- `docs/index.html`: the GitHub Pages explainer (uses Mermaid from cdnjs for the pipeline diagram)
- `demo/index.html`: the prototype tool, hand-built as the reference the `ek-shell` and feature skills will be extracted from

## Phase 1, step 1 — ek-ingest-presentation (started 2026-10-23)
- `skills/ek-ingest-presentation/ingest.py` exists and runs end to end: text per page (pdftotext when poppler is on PATH, else PyMuPDF), 1600 px renders, fonts, measured palette, keyword auto-tags, year / area / option / storey regexes, duplicate-page hashing, `work/extract.json` + `work/brief.skeleton.json`. Pinned deps in `requirements.txt`. OCR via Tesseract when installed; otherwise image-only pages are flagged `needs_ocr` and the model reads the renders.
- Reviewed once by all three QC agents (security: fix, critic: revise, debugger: fix); every blocking finding was closed in one revision. Threat model: `work/security/ek-ingest-presentation.md`. Log: `work/log.md`.
- **Tested on 1 real deck, not the 3 the work plan asks for**, and that deck is the Engage Kit mid-term pitch itself, not an architectural pre-design deck. No pre-design deck exists on the machine. The resulting `work/brief.json` is therefore honest but nearly empty (no site, history, program, options). First thing next session: get 2–3 real pre-design decks (PDF) into `input/` and re-run.
- Lesson from the first deck: every page was a rasterised image with no text layer, so pdftotext would have returned nothing. Expect this from decks exported from InDesign / Miro / Figma; OCR or visual reading is the normal path, not an edge case. Tesseract is not installed here (winget `tesseract-ocr.tesseract` would add it; nobody has installed it).
- Bug found and fixed on the way: the palette quantiser overflowed 8-bit integers and reported white as near-black / cyan.
- Data rule added (qc-security): `input/`, `work/slides/`, `work/extract.json`, `work/brief.skeleton.json` are gitignored because they hold verbatim client material; `work/brief.json` is committed only after a person checks it for personal data. Renders that later skills embed as `history[].image` / `plan_image` may contain photos of residents; the team must decide what is published.

The Contract in `skills/ek-shell/SKILL.md` is what every feature skill and QC agent now builds against.
- Extracted from `demo/index.html`, which is unchanged. What left the shell comes back through feature skills: timeline, massing, program and synthesis sections; the SVG image bank; three.js; the voice recorder (via `EK.registerKind('voice', …)`).
- `output/index.html` is the Riverside sample with all slots empty ("not built yet"). It is a container, not a tool yet.
- One QC round (security block → critic revise → debugger fix), all blocking findings closed in one revision: typeface string validated before it reaches `<style>`; malformed stored reactions dropped on load; Google Fonts off by default (opt-in `project.font_link: "google"` in the manifest); welcome card states what is collected and offers Remove all; mute grey meets 4.5:1 in both schemes; desktop bar no longer covers the rail; palette keys `marker`/`plan` accepted as aliases of `accent1`/`accent2`; welcome copy derived from installed features; bar context on welcome is the brief's first decision point. Not re-reviewed by the agents after the revision; re-verified by the orchestrator in the browser.

- Typeface: the sample now renders in the system stack, not Archivo, because the third-party font request is opt-in. Self-hosting Archivo via `@font-face` is the clean fix (Phase 1 follow-up).
- Local preview: `python -m http.server 8765 --directory engage-kit` from the parent folder, then `http://localhost:8765/output/index.html`.

## Phase 1, step 3 — ek-timeline (2026-10-25)
- First feature in a shell slot, built as a scroll story at the person's request (full-bleed image per moment, floating caption, year rail), not the session-0 horizontal axis. `skills/ek-timeline/build.py` writes the section, style and script into `output/index.html` from `brief.history`; idempotent; images embedded as data URIs behind `<img>`.
- One QC round (security fix → critic revise → debugger fix), all blocking findings closed in one revision; details in `work/log.md`, threat model in `work/security/ek-timeline.md`. Not re-reviewed by the agents after the revision; re-verified by the orchestrator in the browser at 1200×900 and 375×812.
- **What a real project must know:** full-bleed cover crops a 4:3 slide by about half on a phone, so supply portrait or square images (≥1200 px short side, subject in the centre 3:4) and never bake captions into them; the sample's flat SVGs show the problem. Photos of identifiable people need clearance before a public URL. Twelve 1400 px JPEGs are roughly 2–3 MB of page; the build warns above 1.5 MB of images.
- **Copy and voice:** the tool only says "speak" once `ek-voice-reactions` has registered a voice kind at runtime; until that skill is built the lede, toast and privacy card say "type". The welcome lede now also says the team "collects it and adds it to the record", matching what the shell actually does (device-local until collected).
- Contract changes made while building the first feature: bare `<!-- ek:scripts -->` marker; CSS in a feature's own `<style data-feature>` at `<!-- ek:styles -->`; `EK.context(feature, target, hint, label)`; `EK.hasKind(kind)`; `data-with-voice` / `data-without-voice` attributes resolved on load; full-bleed recipe. These are in `skills/ek-shell/SKILL.md`.
- Unverified in the harness: the `:focus-visible` outline on the story region (programmatic focus does not trigger it) and the smooth-scroll animation (disabled in the test browser). Check both on a real phone and a laptop before a session.

## Phase 1, step 4 — ek-program-diagram (2026-10-25)
- Full-frame treemap of the proposed spaces with a docked card (under the map on phones, beside it on desktop): what a space is for, proposed area, this phone's suggestion, slide number; − / + record `edit` reactions, Reset removes them; "Rank my top five" records `vote` reactions. The map is laid out from the proposed areas and never re-flows; the visitor's suggested size is a dashed outline over the block.
- One QC round (security fix → critic revise → debugger fix), all blocking findings closed in one revision; details in `work/log.md`, threat model in `work/security/ek-program-diagram.md`. Re-verified by the orchestrator at 1200×900 and 375×812.
- **Per-device cap:** one phone can move a space at most ±5 steps (±100 m² at the default 20 m² step). Adjustments and ranks are summed per device, and the card says "(this phone)". The team must decide, once a sync target exists, how synthesis reports the number of devices behind each total.
- Shell additions: `EK.fitStage(el, featureId, {onResize})` with `ek-stage` / `ek-bleed` (the timeline now uses it too), the `ek:context` event, and tour steps sorted by section order.
- Known limits: on a 375 px phone two narrow blocks (Community kitchen, Riverside terrace) carry no visible label; their accessible names are complete. The test pane does not deliver ResizeObserver callbacks, so bar-growth re-sizing is timer-driven and was verified that way.

## Phase 1, step 5 — ek-site-massing-3d (2026-10-26)
- Full-frame three.js viewer: ground, context blocks from `context_blocks`, the current option's massing in the project blue, selected block in the accent, sun shadows; docked card with option tabs, one-choice-per-phone vote ("✓ My choice"), sun slider, Eye level (camera at 1.6 m) / Back to overview, and a study note. Pin and adjust are left to `ek-massing-markup`, which gets `EK.feature.massing` and an empty `[data-slot="massing-modes"]` row.
- One QC round (security fix → critic revise → debugger fix), all blocking findings closed in one revision; details in `work/log.md`, threat model in `work/security/ek-site-massing-3d.md`. Re-verified by the orchestrator at 1200×900 and 375×812; the no-library and bad-SRI fallbacks were verified by the debugger.
- **Third-party request:** every visit fetches three.js r128 (603 KB) from cdnjs.cloudflare.com, pinned with an SRI hash computed from the downloaded bytes on 2026-10-26 (`sha384-CI3E…WWdHu`); Cloudflare sees the visitor's IP, user agent and the tool's URL. Self-hosting `three.min.js` beside `index.html` is the alternative for a drop-in session with no network; the fallback then shows the deck's drawing and voting still works. The hash was not cross-checked against the npm `three@0.128.0` package; do that once.
- **Honesty over looks:** no river, street or site line is drawn because the brief schema carries no site geometry; the card says so. A real project that wants them supplies `site.outline_m` (a polygon in metres) and context in `context_blocks`. Storey height 3.4 m is a stated assumption.
- Known limits: on a 375 px phone the card still scrolls a little (sun and eye level sit below a faded edge until scrolled); the harness could not show the height animation or verify reduced motion beyond reading the code.

## Phase 1, step 6 — ek-voice-reactions (2026-10-26)
- A bar kind, not a section: hold-to-record or tap-to-start / tap-to-stop on the shell's round mic button, 60 s cap with a countdown, review row (player, length, Keep / Delete), nothing stored until Keep. Consent card before every visitor's first recording (in memory only, again after 10 minutes idle), as a screen-reader dialog, saying: up to 60 s; stays on this phone until collected; the design team and the client listen to it for the project record; anyone using this phone today can play it back (with the count already here); remove everything from the Start page; don't record other people; typing is always an option.
- Fallbacks: no recorder / insecure context → typed button at load; microphone blocked → typed button with a toast that says how to allow it; a clip the phone cannot store is refused plainly (the shell now reports a failed storage write instead of pretending).
- One QC round (first launch of all three agents stalled; the retry gave security fix → critic revise → debugger fix); all blocking findings closed in one revision; details in `work/log.md`, threat model in `work/security/ek-voice-reactions.md`. **Not verified anywhere yet: a real recording.** The test browser blocks the microphone, so capture was exercised with a stubbed recorder only. Test on a real phone over HTTPS (GitHub Pages) before any session; the 60 s auto-stop and the level meter are untested.
- **Table script the team must settle (voice is personal information under PIPA in BC; FIPPA if the client is a municipality):** purpose (hear reactions in residents' own words for the design record); who hears it (team and client; machine transcripts labelled draft); where it lives (this phone until the end of the day, then copied off and the phone wiped with Remove all); retention after collection (set a date, e.g. deleted after synthesis sign-off); how to remove (ask the named team member); no recording of other people, and no children without a parent present. Decide whether earlier visitors' clips stay playable on a table phone or the team collects and wipes between visitors.
- Hosting for the mic: `getUserMedia` needs a secure context. GitHub Pages (HTTPS) and `localhost` work; a LAN `http://` address silently degrades to typing; `file://` works in Chrome and Firefox, is unreliable in Safari. Pre-grant the microphone on each table phone during setup.
- Not done: per-clip delete in the timeline's memories (Remove all on the Start page is the only removal today); transcription (synthesis, at export).

## Known gaps (honest list)
- Skills are instruction drafts except `ek-ingest-presentation` (script, run once), `ek-shell` (template + build), `ek-timeline`, `ek-program-diagram`, `ek-site-massing-3d` and `ek-voice-reactions` (build, run on the sample). Phase 1 continues with `ek-massing-markup`, then `ek-feedback-synthesis`.
- The prototype's 3D viewer was syntax-checked but not rendered in the session-0 sandbox (no network for the CDN); the fallback message path was tested there. **Verified 2026-10-23 on the published Pages site in a Chromium browser:** three.js r128 loads from cdnjs, the massing viewer renders (site, river, context, options A/B/C), the Mermaid diagram on the explainer renders, and the `#tour` deep link plays all nine steps and cleans up its sample reactions on Finish. No console errors. One observation, not fixed: the shell reads the hash only on page load, so changing the hash in an already-open tab does not switch sections (navigation buttons do).
- Voice recording cannot be tested headless. In the published artifact the microphone may be blocked by the viewer sandbox; the control then switches to the typed fallback by design. For a live demo of voice, open `demo/index.html` directly in a browser.
- Illustrations (site plan, three option axons, one drawing per history event) are generated SVGs in `demo/illustrations/` (`generate.py` rebuilds them). A real project replaces them with the deck's own renders via `ek-ingest-presentation`.
- Reactions are device-local. Multi-device merge is Phase 2.
- Sample content (Riverside Community Hub) is invented.
